# Security Assessment

The application is not production-secure as written. The following findings were
identified during a source review.

| Severity | Issue | Evidence | Recommendation |
| --- | --- | --- | --- |
| High | Verification tokens are six-digit, generated by a non-cryptographic random source, and have neither expiry nor attempt limits. | `module-infrastructure/src/main/kotlin/com/example/eventonboarding/infrastructure/token/RandomTokenGenerator.kt:10`; `module-onboarding-token-verification/src/main/kotlin/com/example/eventonboarding/tokenverification/TokenVerification.kt:14-20` | Use `SecureRandom`, persist an expiry and failed-attempt count, and rate-limit verification by application and client IP. |
| High | Onboarding IDs act as bearer credentials without authentication. | `module-onboarding-email/src/main/kotlin/com/example/eventonboarding/email/EmailOnboardingController.kt:24-25`; scoring and other state-changing endpoints similarly accept only the application ID. | Bind onboarding access to a server-side session or a signed, short-lived, scoped token. Avoid putting bearer credentials in URL paths, which may be captured by access logs. |
| Medium | Unauthenticated onboarding creation can consume unbounded in-memory state and flood logs. | `POST /api/onboarding/start` creates records retained by `InMemoryApplicationRepository` until restart. | Rate-limit and quota application creation, expire stale workflows, and use persistent storage. |
| Medium | Enabling the `e2e` Spring profile exposes a fixed password and a public endpoint that configures every verification token. | `module-application/src/main/kotlin/com/example/eventonboarding/application/E2eTestConfiguration.kt:23-40,60-73` | Prevent the `e2e` profile from being enabled in production with deployment policy and startup configuration validation. Prefer test-only artifacts. |
| Medium | Docker Compose publishes management and supporting services with development defaults. | `compose.yaml:5-10,22-24,29-34` exposes RabbitMQ management with `guest/guest`, Apicurio without authentication, and SonarQube. | Bind services to loopback or an internal network, require authentication, manage credentials as secrets, and do not deploy this Compose configuration to production. |
| Low | Next.js dependencies use mutable `latest` version tags. | `fe-next/package.json:14-23` | Pin package versions. The lockfile helps reproducibility but does not prevent unreviewed updates when the lockfile is refreshed. |

## Existing positive controls

- Account passwords are generated with `SecureRandom` and stored with BCrypt.
- API responses omit verification tokens.
- The reviewed Next.js and Vue rendering paths have no direct XSS sink.
- The account credential notifier masks the password, although the README currently
  describes it as printing credentials.

## Sensitive logging

Verification tokens are logged in plaintext by
`module-infrastructure/src/main/kotlin/com/example/eventonboarding/infrastructure/notification/ConsoleVerificationNotifier.kt:12-13`.
Replace console delivery with an appropriate protected delivery channel and ensure
logs do not receive authentication secrets.
